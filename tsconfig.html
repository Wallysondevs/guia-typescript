O tsconfig.json

O tsconfig.json é o painel de controle do compilador: diz onde estão os arquivos, para onde vai o JavaScript e quão exigente o TypeScript deve ser. Você criou o seu com npx tsc --init lá no começo; agora vamos entender as opções que mais aparecem no dia a dia.

Você vai aprender
  • O que significam as linhas do tsconfig.json do projeto.
  • O que o strict liga.
  • noUncheckedIndexedAccess e exactOptionalPropertyTypes.
  • Por que o tsc gera JavaScript mesmo com erro, e como impedir.
  • Passar opções pela linha de comando.

1. As linhas ativas do projeto

Tirando os comentários, o tsconfig.json do nosso projeto (gerado pelo TypeScript 7.0.2, com rootDir e outDir descomentados) fica assim:

{
  "compilerOptions": {
    "rootDir": "./src",
    "outDir": "./dist",
    "module": "nodenext",
    "target": "esnext",
    "types": [],
    "sourceMap": true,
    "declaration": true,
    "declarationMap": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "strict": true,
    "jsx": "react-jsx",
    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "noUncheckedSideEffectImports": true,
    "moduleDetection": "force",
    "skipLibCheck": true,
  }
}
rootDir / outDir
de onde vêm os .ts (src) e para onde vão os .js (dist).
module / target
que sistema de módulos usar (nodenext: o do Node atual) e para qual versão do JavaScript gerar (esnext: a mais nova).
types: []
não carrega pacotes @types automaticamente (veja a aula de tipos de pacotes).
sourceMap, declaration, declarationMap
geram os .js.map, .d.ts e .d.ts.map que aparecem em dist/.
strict
liga um pacote de verificações rigorosas.
verbatimModuleSyntax, isolatedModules
exigem que cada arquivo possa ser convertido sozinho (por isso o import type).
skipLibCheck
não confere os .d.ts de bibliotecas, o que deixa a compilação mais rápida.
Comentários e vírgula sobrando

O tsconfig.json aceita comentários // e vírgula depois do último item, coisas que um JSON comum não aceita.

2. O que o strict liga

Este código tem dois problemas escondidos: um parâmetro sem tipo e um valor que pode ser null.

function dobrar(x) {
  return x * 2;
}
const achado: string | null = Math.random() > 2 ? "ok" : null;
console.log(dobrar(4), achado.length);

Toda opção do tsconfig.json também pode ir na linha de comando. Primeiro, tentando desligar só o strict:

$ npx tsc --strict false
tsconfig.json(25,5): error TS5052: Option 'exactOptionalPropertyTypes' cannot be specified without specifying option 'strictNullChecks'.

As opções dependem umas das outras: exactOptionalPropertyTypes só existe junto com strictNullChecks, que vem do strict. Desligando as duas:

$ npx tsc --strict false --exactOptionalPropertyTypes false

Nenhuma reclamação. Agora com o tsconfig.json normal:

$ npx tsc
src/strict.ts(1,17): error TS7006: Parameter 'x' implicitly has an 'any' type.
src/strict.ts(5,24): error TS18047: 'achado' is possibly 'null'.
$ node dist/strict.js
file:///home/ana/projeto/dist/strict.js:5
console.log(dobrar(4), achado.length);
                              ^

TypeError: Cannot read properties of null (reading 'length')
    at file:///home/ana/projeto/dist/strict.js:5:31
    at ModuleJob.run (node:internal/modules/esm/module_job:561:25)
    at async node:internal/modules/esm/loader:647:26
    at async asyncRunEntryPointWithESMLoader (node:internal/modules/run_main:101:5)

Node.js v24.22.1

Com strict, vêm noImplicitAny (o TS7006) e strictNullChecks (o TS18047), entre outras. E repare na última linha: mesmo com erro, o tsc gerou o JavaScript, e o programa quebrou rodando. Isso é o assunto da seção 5.

3. noUncheckedIndexedAccess

Ler lista[0] pode dar undefined se a lista estiver vazia. Com esta opção ligada, o TypeScript lembra disso:

const nomes: string[] = [];
const primeiro = nomes[0];
console.log(primeiro.toUpperCase());
$ npx tsc
src/indice.ts(3,13): error TS18048: 'primeiro' is possibly 'undefined'.

O tipo de primeiro é string | undefined. A correção é tratar o caso: primeiro?.toUpperCase(), primeiro ?? "ninguém" ou um if.

4. exactOptionalPropertyTypes

Uma propriedade opcional (apelido?: string) pode faltar. Com esta opção, ela não pode ser escrita como undefined:

type Perfil = { nome: string; apelido?: string };
const ana: Perfil = { nome: "Ana" };
const duda: Perfil = { nome: "Duda", apelido: undefined };
console.log(ana, duda);
$ npx tsc
src/opcional.ts(3,7): error TS2375: Type '{ nome: string; apelido: undefined; }' is not assignable to type 'Perfil' with 'exactOptionalPropertyTypes: true'. Consider adding 'undefined' to the types of the target's properties.
  Types of property 'apelido' are incompatible.
    Type 'undefined' is not assignable to type 'string'.

A mensagem já dá a saída: se você quer permitir undefined escrito, declare apelido?: string | undefined. Ou simplesmente não escreva a propriedade.

5. noEmitOnError e noEmit

Por padrão, o tsc avisa os erros e gera o JavaScript mesmo assim. Veja:

const idade: number = "trinta";
console.log(idade);
$ npx tsc
src/emite.ts(1,7): error TS2322: Type 'string' is not assignable to type 'number'.
$ ls dist
emite.d.ts
emite.d.ts.map
emite.js
emite.js.map
$ node dist/emite.js
trinta

Com --noEmitOnError (ou "noEmitOnError": true no tsconfig.json), se houver erro nada é gerado:

$ npx tsc --noEmitOnError
src/emite.ts(1,7): error TS2322: Type 'string' is not assignable to type 'number'.
$ ls dist
ls: cannot access 'dist': No such file or directory

E o --noEmit só confere os tipos, sem gerar nada (útil para checar rápido):

console.log("tudo certo");
$ npx tsc --noEmit
$ ls
node_modules
package-lock.json
package.json
src
tsconfig.json

Nenhuma saída e nenhuma pasta dist: deu tudo certo e nada foi gerado.

Quando dá errado

Nome de opção com erro de digitação 
{
  "compilerOptions": {
    "rootDir": "./src",
    "outDir": "./dist",
    "module": "nodenext",
    "stric": true
  }
}
$ npx tsc
tsconfig.json(6,5): error TS5023: Unknown compiler option 'stric'.

O compilador não ignora opções desconhecidas: ele avisa com o TS5023 e aponta a linha do tsconfig.json.

Missões

Missão: a fila pode estar vazia. Corrija o código para compilar com noUncheckedIndexedAccess e mostrar Primeiro da fila: ninguém quando não houver ninguém (dica: ??).

const fila: string[] = [];
const primeiro: string = fila[0];
console.log("Primeiro da fila: " + primeiro);

const fila: string[] = [];
const primeiro: string = fila[0] ?? "ninguém";
console.log("Primeiro da fila: " + primeiro);

Primeiro da fila: ninguém

Missão: sem mexer no objeto, mude o tipo Item para que cor aceite undefined escrito. Saída esperada: { nome: 'Caneta', cor: undefined }.

type Item = { nome: string; cor?: string };
const item: Item = { nome: "Caneta", cor: undefined };
console.log(item);

type Item = { nome: string; cor?: string | undefined };
const item: Item = { nome: "Caneta", cor: undefined };
console.log(item);

{ nome: 'Caneta', cor: undefined }

Resumo

  • O tsconfig.json diz onde estão os arquivos, para onde vai o JS e quão rigoroso é o compilador.
  • strict traz noImplicitAny e strictNullChecks, entre outras.
  • noUncheckedIndexedAccess e exactOptionalPropertyTypes deixam o tipo mais honesto.
  • Por padrão o JS sai mesmo com erro; use noEmitOnError ou noEmit.
