Discriminated Unions

Uma das ideias mais úteis do TypeScript: dar a cada variação de um tipo uma etiqueta (um campo como tipo: "circulo"). Com ela, um switch sabe exatamente com qual variação está lidando, e o compilador avisa se você esquecer algum caso.

Você vai aprender
  • Montar uma union com um campo etiqueta em comum.
  • Fazer narrowing com switch e if pela etiqueta.
  • Checagem de exaustividade com never.
  • Modelar estados (carregando, sucesso, erro) sem campos “talvez”.

1. A etiqueta

type Circulo = { tipo: "circulo"; raio: number };
type Retangulo = { tipo: "retangulo"; largura: number; altura: number };
type Forma = Circulo | Retangulo;

function area(f: Forma): number {
  switch (f.tipo) {
    case "circulo":
      return Math.PI * f.raio ** 2;
    case "retangulo":
      return f.largura * f.altura;
  }
}

console.log(area({ tipo: "circulo", raio: 1 }).toFixed(2));
console.log(area({ tipo: "retangulo", largura: 3, altura: 4 }));

2. Nenhum caso esquecido: never

Quando surge uma variação nova, é fácil esquecer de tratá-la. O truque: no default, guardar a variável num never. Se sobrar algum caso, ele não cabe em never e o compilador reclama:

type Forma =
  | { tipo: "circulo"; raio: number }
  | { tipo: "retangulo"; largura: number; altura: number }
  | { tipo: "triangulo"; base: number; altura: number };

function area(f: Forma): number {
  switch (f.tipo) {
    case "circulo":
      return Math.PI * f.raio ** 2;
    case "retangulo":
      return f.largura * f.altura;
    default:
      const sobrou: never = f;
      throw new Error("forma desconhecida: " + JSON.stringify(sobrou));
  }
}
$ npx tsc
src/exaustivo.ts(13,13): error TS2322: Type '{ tipo: "triangulo"; base: number; altura: number; }' is not assignable to type 'never'.

O erro diz exatamente quem ficou de fora: o triângulo. Ao adicionar o case "triangulo", o erro some.

3. Modelando estados

Em vez de um objeto cheio de campos opcionais (dados?, erro?, carregando?), cada estado traz só o que faz sentido para ele:

type Estado =
  | { status: "carregando" }
  | { status: "sucesso"; dados: string[] }
  | { status: "erro"; mensagem: string };

function mostrar(e: Estado): string {
  if (e.status === "carregando") return "Carregando...";
  if (e.status === "erro") return "Falhou: " + e.mensagem;
  return `${e.dados.length} itens: ${e.dados.join(", ")}`;
}

console.log(mostrar({ status: "carregando" }));
console.log(mostrar({ status: "sucesso", dados: ["pão", "leite"] }));
console.log(mostrar({ status: "erro", mensagem: "sem internet" }));
$ npx tsc && node dist/estado.js
Carregando...
2 itens: pão, leite
Falhou: sem internet

Depois dos dois if, só sobrou "sucesso", então e.dados está liberado. E é impossível criar um estado de erro sem mensagem:

type Estado =
  | { status: "carregando" }
  | { status: "sucesso"; dados: string[] }
  | { status: "erro"; mensagem: string };

const e: Estado = { status: "erro" };
$ npx tsc
src/invalido.ts(6,7): error TS2322: Type '{ status: "erro"; }' is not assignable to type 'Estado'.
  Property 'mensagem' is missing in type '{ status: "erro"; }' but required in type '{ status: "erro"; mensagem: string; }'.

Quando dá errado

Etiqueta com tipo string em vez de literal

Se a etiqueta for string em vez de um literal, o TypeScript não consegue separar as variações:

type Cachorro = { especie: string; late: boolean };
type Gato = { especie: string; mia: boolean };

function som(a: Cachorro | Gato) {
  if (a.especie === "cachorro") {
    return a.late;
  }
  return false;
}
$ npx tsc
src/etiqueta-fraca.ts(6,14): error TS2339: Property 'late' does not exist on type 'Cachorro | Gato'.
  Property 'late' does not exist on type 'Gato'.

A correção é usar literais: especie: "cachorro" e especie: "gato".

Resumo

  • Uma etiqueta (mesmo campo, literal diferente) separa as variações de uma union.
  • switch/if pela etiqueta faz o narrowing.
  • const n: never = x no default acusa casos esquecidos.
  • Estados com etiqueta evitam campos opcionais confusos.
